# Ludo Vortex implementation handoff

This handoff records what the Ludo launch epic (`tasks/epics/15-ludo-launch/`) built, which test backs each claim, and what remains before the game can be released. Ludo is the sixth Flutter client in `apps-native/games`, registry id `ludo`, technical ids `app.w3dev.ludo` and `app.w3dev.ludo.debug`. It supersedes the earlier Unity 3D effort at `apps-native/unity/ludo/`, which is frozen and untouched. The product name Ludo Vortex, the knowledge base at `.agents/games/ludo-vortex/`, and the task history in `tasks/epics/15-ludo-launch/STATUS.md` are the other places to look.

The architecture, path map, frozen rulesets and contract matrix are in the [Ludo Flutter plan](../ludo-flutter-plan). The step-by-step list a human follows to provision services and verify a physical device is the [Ludo release checklist](../ludo-release-checklist); it is the document task 29 executes. Source provenance is recorded in [ludo.json](../sources/ludo.json). Economy design is in [Ludo economy](../ludo-economy), and the store compliance drafts are [privacy policy](../ludo-privacy-policy), [data safety](../ludo-data-safety), [content rating](../ludo-content-rating) and [store listing](../ludo-store-listing).

**Status on 2026-10-16.** Tasks 00 to 28 are complete except 26f (the human economy art session, skipped by the user on 2026-10-16, with code-drawn fallbacks in its place). Local play was signed off on a physical device at task 13. Everything online and every economy provider path was built and tested against fakes, in-memory stores and a gated Postgres suite; none of it has touched a real Firebase project, database, RevenueCat project or AdMob account. Task 29 (human, physical-device acceptance and provisioning) is open. No store listing exists, nothing is submitted, and nothing here grants store publication.

## Ownership and boundaries

Owners are the roles in the epic `STATUS.md`. The epic ran as one workflow, so these are logical owners, not named people.

| Logical owner | Owns | Required handoff contract |
|---|---|---|
| `ludo-domain` | `apps-native/games/packages/ludo_rules` | Pure Dart rules: versioned `LudoRuleset`, injected dice, replay events, bots; no Flutter, Flame or SDK imports |
| `ludo-client` | `apps-native/games/ludo` | Flutter and Flame composition, screens, local save, online client, audio, accessibility, telemetry |
| `ludo-service` | `packages/api/src/games/ludo`, `packages/db` Ludo tables | Server-authoritative engine, transactional command service, timeouts, matchmaking, rooms, fanout, wallet and economy routes |
| `ludo-content` | `apps-native/games/ludo/assets`, `content/manifest.json`, `lib/src/assets/ludo_art_manifest.dart` | Named art and audio slots; original or CC0 assets only with provenance in the `LICENSES.md` files; slots awaiting task 26f art listed below |
| `ludo-release` | `apps-native/games/ludo/android`, `docs-internal/gaming/ludo-*.md`, Play, Firebase, RevenueCat and AdMob consoles | Independent version and build, device evidence, privacy and store drafts, provisioning, feature gates |

The pure rules package cannot import Flutter, Flame or SDKs. The server must never trust a client roll, a client-reported rules version, or a client-computed balance. Generic game isolation lives in `packages/api/src/games`; the Ludo-specific routes are mounted in `packages/api/src/index.ts`.

## Requirement ledger

Conventions are those of the other game handoffs. `yes` means the requirement is specified, built, or verified as the column says. `partial` means there is repository code or a testable slice but a stated part is missing. `no` means no evidence in this worktree. `enabled` means an explicit release gate, not that a debug button exists; because task 29 and every store gate are open, **no row is enabled**. Every `implemented` or `verified` claim names the file that backs it. A `verified` value of `partial` or `yes` means an automated test passes against fakes unless the cell says a device did it. Device-verified is stated separately.

## Findings that change the plan for task 29

These came out of writing the ledger. Details and the exact fix location are in the plan's "Known gaps" section.

1. **Firebase will not initialize on Android yet.** The `com.google.gms.google-services` Gradle plugin is not applied in `apps-native/games/ludo/android`, so placing `google-services.json` alone does nothing. A small follow-up code task is needed before the first online device run.
2. **The client's single API base URL cannot reach both sign-in and the Ludo routes.** `LudoGateway` resolves `api/auth/exchange` but `games/ludo/<environment>/...` against the same base, and the deployed API serves both under `/api/`. Found by reading `apps-native/games/ludo/lib/src/net/ludo_gateway.dart` and `ludo_http.dart`; `apps-native/games/ludo/test/net/ludo_gateway_test.dart` cannot see it (fixture transport keyed by relative path). It is not tried against a live server, so treat it as a strong suspect until the first real run. A small code fix is needed before online device testing.
3. **`bun run games:build` cannot produce an online or store-capable APK.** It passes only `GAME_ENVIRONMENT` and `APP_VERSION`. The online and economy passes need a direct `flutter build apk` with `LUDO_API_BASE_URL`, `REVENUECAT_API_KEY` and the AdMob defines. The [release checklist](../ludo-release-checklist) gives the exact command.
4. **Six Ludo migrations exist, not one** (`packages/db/migrations/0005` to `0010`). Task 29's text says no later task added a migration; that is out of date.
5. **Environment variables are only partly documented** in `docs-internal/setup/02-env-vars.md`: `GAME_TOKEN_SECRET_LUDO_<ENV>`, `LUDO_MATCHMAKING_BOT_FILL_SECONDS` and `LUDO_ROOM_EXPIRY_HOURS` are not in that table. The release checklist is complete.
6. **Firestore security rules are not in the repository.**

## Public documentation

No public how-to-play page was added. The check for an existing convention (task 28) found that `docs-public/` holds a getting-started tab, a troubleshooting tab, a support tab (FAQ and known issues) and a legal tab with one page (`legal/glow-rescue-privacy-policy.md`, the privacy policy for the Merge Relay brand Glow Rescue). ## Release and unresolved gates

Google Play and Android first; iOS later. Everything in the [release checklist](../ludo-release-checklist) is open. Unresolved and not decided by this epic: trademark clearance for "Ludo Vortex", developer account type and the closed-test requirement, privacy policy hosting and support email, account and data deletion path, content rating outcome with simulated gambling, Play signing and the upload keystore, localization, quick chat and emoji, and the extra modes (Rush, 1 Kill Win, Mask). The full list with owners is `.agents/games/ludo-vortex/open-questions.md`. Store registration, submission and publication remain separate explicit approvals and are not granted by any task in this epic.
